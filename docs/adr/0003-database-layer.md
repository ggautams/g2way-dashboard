# ADR-0003: The dashboard database layer

Date: 2026-09-23 · Status: accepted · Refines: ADR-0001 §3

## Context

ADR-0001 chose SQLite by default and Postgres by driver swap, via Drizzle, with
"one Drizzle schema serving both". In practice Drizzle's table builders are
dialect-typed: `sqliteTable` and `pgTable` are different types with different
column builders (`integer({ mode: 'boolean' })` against `boolean()`, `text({ mode:
'json' })` against `jsonb()`), and drizzle-kit generates migrations per dialect.
There is no single declaration both drivers accept. The decision needs a concrete
shape so later sessions don't each invent one.

## Decisions

1. **Two schema files, one schema.** `src/lib/db/schema/sqlite.ts` and
   `src/lib/db/schema/pg.ts` declare the same tables, same export names, same
   column names, nullability, keys and indexes. Shared constants (the role list,
   the JSON value type) live in `schema/shared.ts`. `schema/schema.test.ts` fails
   if the two disagree on any of that, or if a row of either reads back as a
   different TypeScript type. Changing the schema means editing both files in the
   same commit; the parity test is what makes "one schema" true.

2. **Portable column types only.** Ids are text UUIDs generated in the app, not
   database sequences. Timestamps are `Date` in TypeScript (`timestamp_ms` integer
   in SQLite, `timestamptz` in Postgres). JSON is `text` JSON in SQLite, `jsonb` in
   Postgres. Enumerations (roles) are `text` with a TypeScript enum, never a
   Postgres enum type, so a new role needs no migration.

3. **Every table carries a non-null `org_id` with no default.** The caller
   supplies it from config (`G2_ORG_ID`), never a literal. The parity test asserts
   it for every table.

4. **`DATABASE_URL` selects the driver** (`src/lib/db/config.ts`): unset means
   SQLite at `./data/dashboard.db`; `file:<path>` is SQLite at that path;
   `postgres://` or `postgresql://` is Postgres via `pg`. Anything else is a
   startup error that never echoes the value, since a Postgres URL carries a
   password.

5. **One migration tree per dialect**, generated by drizzle-kit from
   `drizzle.sqlite.config.ts` and `drizzle.pg.config.ts` into `drizzle/sqlite/`
   and `drizzle/pg/` (`make db-generate`, which runs both). Migrations are
   committed and applied by drizzle-orm's migrator on server start
   (`src/instrumentation.ts`, Node.js runtime only) and by `make db-migrate`.
   Both paths call the same `migrateDatabase()`.

6. **The handle is a tagged union.** `getDatabase()` (server-only, lazy,
   process-wide) returns a union tagged by `dialect` (`'sqlite'` or
   `'postgres'`), each side carrying its own `db` and `schema`, typed together. Data-access
   code narrows on `dialect` and uses the schema object from the handle, never
   imports one dialect's tables directly. We do not cast one dialect's database to
   the other's type to avoid the branch: that lie would type-check and then fail
   at runtime on the first dialect-specific call (SQLite's synchronous `.all()` and
   `.get()`, for instance).

7. **Tests need no database server.** SQLite runs in memory. The Postgres
   migrations are applied to PGlite (Postgres compiled to WASM) in the plain test
   run, which proves `drizzle/pg/` is valid Postgres. The node-postgres driver
   itself is tested against a live server only under `make test-pg` (Docker).

## Consequences

- A schema change is four artefacts: two schema files and two generated
  migrations. The parity test catches the first pair drifting; a forgotten
  `make db-generate` shows up as a failing round-trip test once a test touches
  the new column.
- Query code may need a `dialect` branch where the drivers differ. Keep those in
  small data-access modules under `src/lib/db/` so pages and route handlers never
  see the union.
- `better-sqlite3` is a native module and `pg` opens TCP sockets, so the database
  is unavailable on the edge runtime. Nothing in the dashboard runs there.
- Migrations are resolved from `process.cwd()/drizzle`, so the server must be
  started from the project root (true for `next start` and the planned container).
  A standalone output build would need `drizzle/` copied beside it.
